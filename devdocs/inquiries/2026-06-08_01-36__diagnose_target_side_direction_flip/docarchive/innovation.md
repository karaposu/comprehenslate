### Mechanism 2: Absence Recognition
- **Patch-level:** The framework's polysemy principles all address source-side; the target-side counterpart is ABSENT. The Pass 3 verification check is forward-direction-only; the reverse-direction check is ABSENT. The 5 Layer 2 policies include source-side multi-meaning preservation but no target-side accidental-polysemy prevention.
- **Patch-level:** The companion deathbed-room failure case has its own absent-principle (KEEP-SOURCE-TERM-WITH-GLOSS application gate at Pass 3) but is OUT OF SCOPE for this inquiry.
- **Redesign-level (what should exist if designed from scratch):** Translation principles should be BIDIRECTIONAL by design — for every "preserve source X in target" principle, there should be a paired "verify target doesn't add non-source X" principle. The current framework is uni-directional by historical accumulation; the redesign-level move is to PAIR every existing principle with its inverse counterpart and enforce both at Pass 3.5.
- **Redesign-level (already-present-in-different-form):** The no-smoothing policy is implicitly bidirectional in its underlying value (don't let surface preferences distort meaning); the explicit bidirectional framing is what's added here. So the new policy isn't fully novel — it's the explicit articulation of a value the framework already held implicitly.

### Mechanism 3: Domain Transfer
- **Generic (cross-domain):** Software type theory — "covariance vs contravariance" — preserving relationships in one direction doesn't guarantee preserving in the other; bidirectional type-safety requires both. Parallel: bidirectional meaning-safety requires both source→target preservation AND target→source verification.
- **Native (translation studies):** Eugene Nida's dynamic equivalence theory addresses target-naturalization vs source-fidelity; doesn't address target-internal accidental polysemy directly but its emphasis on "would a target reader misread this?" is conceptually adjacent.
- **Contrarian (cross-domain):** Cryptographic verification — sender encrypts (source→target); receiver decrypts and verifies signature (target→source). The verification step is mandatory; without it, the message could be tampered. Parallel: Pass 3.5 Reverse-Read is the verification step that should be mandatory at Pass 3.

### Mechanism 4: Extrapolation
- **Generic:** If the framework adds bidirectional pairing for polysemy now, every other source-side principle (multi-meaning, register-alternation, nazm preservation) might also need target-side counterparts. Future v1.2/v1.3 increments anticipated.
- **Focused:** For Said Nursi corpus, similar target-side direction-flip risks exist in other Turkish-Islamic phrases with directional semantics — "bekâ" (continuity) could be mistranslated as "stagnation"; "iltifat" (turning toward) could be mistranslated as "compliment." Pass 3.5 catches these systematically.
- **Contrarian:** AI-runtime adaptive Pass 3.5 — the AI learns which target phrases have directional dual senses from past corrections; maintains a learned blacklist. Long-horizon; out of scope for the diagnosis.

### Mechanism 5: Lens Shifting
- **Generic:** Under what conditions does target-side accidental polysemy succeed without causing comprehension failure? When the unintended target reading is BENIGN (not in opposite direction; not contradictory; reader's context disambiguates). The HIGH-SEVERITY subcase (direction-flip) is when the unintended reading is OPPOSITE — that's when prevention is mandatory.
- **Focused:** For the casual reader (A4=casual + A1=conversational target audience), an English phrase with two directional readings is MORE confusing than the same phrase for a scholarly reader who has the source to cross-reference. Pass 3.5 Reverse-Read is therefore especially critical at lower scholarly settings — the reader has no fallback.
- **Contrarian:** Under conditions where the source ITSELF is ambiguous (deliberately polysemous), target-side ambiguity might PRESERVE the source's polysemy. So Pass 3.5 needs nuance: target-side ambiguity is OK when it MATCHES source-side ambiguity; problematic when it ADDS readings source doesn't have.
